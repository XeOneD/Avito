# Avito кандидатогенерация

Решение тестового задания: **кандидатогенерация для поиска услуг**.

По поисковому запросу пользователя отбираем **до 50 объявлений-кандидатов** из корпуса 189 212 объявлений. Метрика — **Recall@50**.

**Финальный результат: Recall@50 = 0.7429** на платформе (baseline BM25 top-50 — 0.3165).

---

## Быстрый старт

### 1. Клонируйте репозиторий

```bash
git clone https://github.com/XeOneD/Avito.git
cd Avito
```

```bash
pip install -r requirements.txt
```

### Оптимизация

Ноутбук `05_v3_e5.ipynb` **самодостаточен**: каждая тяжёлая операция выполняется только если соответствующего артефакта нет на диске. Это даёт:

- **Холодный старт** (~2 часа): все артефакты строятся с нуля, модель обучается, генерируется `answer.csv`.
- **Тёплый старт** (~15 минут): если артефакты уже есть, ноутбук пропустит обучение и BM25-индексацию, сразу перейдёт к инференсу.

Если вам нужен **только финальный результат** и вы не хотите ждать полный пайплайн — можно запустить лишь `05_v3_e5.ipynb`: он сам соберёт отсутствующие артефакты.

### Проверка воспроизводимости

## О задаче

Пользователи Авито ищут услуги короткими запросами: «автоподбор», «скупка телевизоров», «баня на дровах», «монтаж видеодомофонов», «обзвон по базе».

Поиск устроен каскадом:
1. **Кандидатогенерация** — быстро отбирает небольшое множество подходящих объявлений из всего корпуса.
2. **Ранжирование** — упорядочивает только отобранных кандидатов.

Главное требование к кандидатогенерации — **полнота**. Если нужное объявление не попало в кандидаты, ранжирование его уже не вернёт.

Наша задача — реализовать этап кандидатогенерации: по запросу отобрать до 50 объявлений для передачи на ранжирование.

## Результаты

| Метод | Честный Recall@50 (val) | Recall@50 (платформа) |
|---|---|---|
| BM25 top-50 (baseline) | 0.3165 | — |
| BM25 top-200 (потолок) | 0.5825 | — |
| BM25 top-500 (потолок) | 0.7674 | — |
| **LightGBM reranker v1** (BM25 top-500) | 0.7458 | 0.6350 |
| **LightGBM reranker v2** (BM25 top-1000 + char-3-gram) | ~0.78 | 0.7405 |
| **LightGBM reranker v3** (+ e5-small) | 0.8662 | **0.7429** |

Финальное решение обгоняет baseline BM25 top-50 в **2.3 раза**.

## Подход

Каскад из двух этапов: **кандидатогенерация** → **реранжирование**.

### 1. Кандидатогенерация — гибридный поиск BM25 + dense

**Три BM25-индекса** (`bm25s`), каждый даёт top-1000 кандидатов:

| Индекс | Что индексирует | Зачем |
|---|---|---|
| `full` | заголовок ×3 + описание + параметры | основной поиск |
| `title` | только заголовок | устойчивость к длинным описаниям |
| `char3` | char-3-граммы заголовка | опечатки, морфология, короткие запросы |

**Dense retrieval (v3):**
- эмбеддинги `intfloat/multilingual-e5-small` (384-мерные);
- FAISS `IndexFlatIP` по эмбеддингам заголовков всех 189k объявлений;
- top-200 e5-кандидатов на запрос.

**Итоговый пул:** объединение top-1000 BM25 (по трём индексам) и top-200 e5 — около 2000–2600 уникальных кандидатов на запрос.

### 2. Реранжирование — LightGBM

23 признака на пару «запрос — объявление»:

**BM25 (6):**
- `bm25_full_score`, `bm25_full_rank`;
- `bm25_title_score`, `bm25_title_rank`;
- `bm25_char3_score`, `bm25_char3_rank`.

**Dense (3):**
- `e5_score`, `e5_rank`, `e5_cos`.

**Пересечения токенов (6):**
- `overlap_recall`, `overlap_jaccard`;
- `title_overlap_recall`, `desc_overlap_recall`, `params_overlap_recall`;
- `char3_jaccard`.

**Совпадения (3):**
- `loc_match`, `cat_match`, `microcat_match`.

**Числовые признаки объявления (5):**
- `item_rating`, `item_reviews`, `item_price_log`, `item_title_len`, `item_desc_len`.

**Модель:** `lightgbm.LGBMClassifier`, `scale_pos_weight` для дисбаланса 1:34, `num_leaves=63`, `learning_rate=0.03`, early stopping по AUC.

## Валидация

**Псевдо-`query_key`** = `search_query + location + delivery + infm_params + category`.
После удаления дублей — **354 463 группы**. Среднее число позитивов на запрос — 1.32 (медиана 1, максимум 278).

**GroupKFold (5 фолдов)** с группировкой по `search_query` — исключает утечку по тексту запроса.

**Честная оценка** на 5 000 отложенных запросов:
1. Берём **все** BM25 top-1000 + e5 top-200 кандидатов.
2. Считаем фичи для **всех** кандидатов (без подмешивания позитивов).
3. Ранжируем моделью, берём top-50, считаем Recall@50.

## Анализ ошибок: почему валидация переоценивает результат

При переходе от v2 к v3 мы получили прирост честного Recall@50 на 5-фолдовой валидации: с ~0.78 до **0.8662**. Однако на платформе результат почти не изменился: 0.7405 → 0.7429.

**Причина — сдвиг распределения между train и benchmark:**

1. e5-эмбеддинги особенно хорошо работают на train-запросах, потому что их лексика часто совпадает с заголовками объявлений.
2. Реранкер, обученный на train, начинает **переоценивать важность e5-фичей** (`e5_score`, `e5_rank`, `e5_cos`).
3. На benchmark-запросах (**63% уникальных формулировок**, отсутствующих в train) это приводит к смещённому ранжированию.

**Урок:** высокая метрика на отложенной выборке из того же распределения не гарантирует перенос на реальные данные. Для защиты нужны:
- отдельная проверка на запросах из другого источника;
- регуляризация, чтобы модель не переоценивала один источник признаков;
- калибровка весов на инференсе.

Несмотря на это, финальное решение уверенно обгоняет baseline: **0.7429 против 0.3165**.

## Ключевые наблюдения

- **`cointegrated/rubert-tiny2` не подходит для retrieval**: cos(rel) = 0.76, cos(irr) = 0.54 — разрыв всего 0.22, dense-only Recall@50 = 0.073. Для сравнения, e5-small даёт разрыв ~0.35.
- **Char-3-граммы** дают основной прирост на коротких запросах («1 с», «3d max», «10 тонник»). Вклад: **+0.105** к Recall@50 между v1 и v2.
- **Расширение пула** с top-500 до top-1000 открыло позитивы, которые реранкер раньше не видел.
- **Русский стемминг** критичен: без него BM25 показывает ~0.25 вместо 0.32.
- **Оптимизация подсчёта признаков**: замена `np.where(ids == ip)` на предвычисленные словари `{item_pos: rank}` ускорила цикл по 10M пар в ~20 раз.

## Использованные библиотеки

- `bm25s` — быстрая реализация Okapi BM25.
- `intfloat/multilingual-e5-small` — эмбеддинги для dense retrieval.
- `faiss-cpu` — ANN-поиск по эмбеддингам.
- `lightgbm` — градиентный бустинг, финальный реранкер.
- `nltk.stem.snowball.RussianStemmer` — стемминг.
- `transformers`, `torch` — инференс e5-small на CPU.
- `pandas`, `numpy`, `pyarrow` — обработка данных.

Внешние API не используются. Всё воспроизводится локально на CPU.

## Что можно улучшить

1. **Кросс-доменная валидация** — собрать отдельный набор запросов, максимально непохожих на train, калибровать на нём.
2. **Hard negative mining** — обучить v4 на негативах, которые модель v3 путает с позитивами.
3. **Более сильная dense-модель**: `BAAI/bge-m3`, `intfloat/multilingual-e5-base` — потенциально +3–5%.
4. **Квантизация модели** — ONNX/quantization e5-small для ускорения инференса.
5. **Отдельные модели по категориям** — разные реранкеры для `item_microcat_id` групп.
