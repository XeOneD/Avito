# Кандидатогенерация для поиска услуг Авито

Тестовое задание на стажировку в Авито. По поисковому запросу нужно отобрать до 50 объявлений из корпуса
в 189 212 услуг. Метрика - Recall@50: ранжирование идёт следующим этапом, и всё, что не попало в эти 50,
пользователь уже не увидит.

Данные: `train.parquet` - 497 673 пары «запрос → выбранное объявление», `benchmark_items.parquet` -
корпус, `benchmark_queries.parquet` - 2 452 запроса, для которых нужен ответ.

## Подход

1. **Кандидаты из нескольких источников**, около 2-3 тысяч на запрос:
   - BM25 по полному тексту объявления (заголовок ×3, описание, параметры), со стеммингом;
   - BM25 только по заголовку;
   - BM25 по символьным 3-граммам заголовка - ловит опечатки и формы слов («1 с» и «1с»);
   - BM25 только по объявлениям из города запроса - у 83% выбранных объявлений город совпадает с городом поиска;
   - плотный поиск на `multilingual-e5-small` - для запросов без общих слов с объявлением.
2. **Ранжирование кандидатов** LightGBM LambdaRank. Признаки: ранги и точные скоры каждого источника,
   косинус e5, доля слов запроса в заголовке / описании / параметрах, совпадение города и категории,
   рейтинг, цена, популярность объявления в train.

BM25 написан на разреженных матрицах scipy (`candgen/bm25.py`, ~60 строк). Так скор BM25 считается для
любой пары запрос-объявление, а не только для попавших в топ, и тем же расчётом берётся топ внутри города.

## Результаты

| Версия | Что изменилось | Валидация | Платформа |
|---|---|---|---|
| BM25 top-50 | бейзлайн | 0.3165 | - |
| v1 | LightGBM поверх BM25 top-500 | 0.7458* | 0.6350 |
| v2 | top-1000, три индекса, char-3-граммы | ~0.78* | 0.7405 |
| v3 | + e5 | 0.8662* | 0.7429 |
| v4 | переписано, см. ниже | см. `reports/` | - |

\* Эти цифры завышены: валидация v1-v3 считалась на тех же запросах, на которых обучалась модель.

### Что было не так в v1-v3

Разрыв между валидацией (0.87) и платформой (0.74) заставил перечитать код. Нашлось:

- **Валидация на обучающих данных.** Финальная модель обучалась на всех запросах, а Recall@50 считался на
  выборке из них же. Теперь запросы делятся по тексту на три части (обучение / ранняя остановка / hold-out),
  и одинаковый текст из разных городов целиком попадает в одну часть.
- **Разный текст запроса при обучении и на инференсе.** При обучении к запросу приклеивались параметры
  поиска (`search_infm_params_text`), на benchmark - нет. Признаки на инференсе имели другое распределение.
  Теперь текст строит одна функция, а параметры поиска стали отдельным признаком.
- **Утечка метки.** Позитивы, которых не было в пуле кандидатов, попадали в обучение с признаками из одних
  нулей - включая ранг 0, «первое место». Такие строки бывали только у позитивов. Теперь в обучение идут
  только кандидаты из пула, и признаки для обучения и инференса считает один и тот же код (это проверяет
  `tests/test_features.py`).
- **Сломанный признак категории.** `search_category` сравнивалась с `item_microcat_id` - это другой
  справочник, признак всегда был 0, к тому же он дублировался.
- **Скор только для своего топа.** Если объявление нашёл заголовочный индекс, но не полнотекстовый, его
  полнотекстовый скор был 0. Теперь все скоры точные.
- **Не использовался город** при отборе кандидатов.
- **Медленно.** Признаки считались циклом по каждой паре (2 часа с нуля). Теперь - матричными операциями.

Цифры v4 на hold-out появятся в `reports/` после запуска `python -m candgen.validate`.

## Запуск

```bash
pip install -r requirements.txt
```

Положите в `dataset/` три parquet-файла из архива задания
(`https://disk.yandex.ru/d/sNhfo0YOjGtufg`).

```bash
python -m candgen.validate     # честная оценка на hold-out → reports/validation_full.md
python -m candgen.submit       # обучение на всех запросах → answer.csv
```

Первый запуск строит индексы и эмбеддинги (e5 на CPU - около 10 минут) и кэширует их в `artifacts/`.
Если huggingface.co недоступен, скачайте модель через зеркало и передайте путь к папке:

```bash
HF_ENDPOINT=https://hf-mirror.com huggingface-cli download intfloat/multilingual-e5-small --local-dir models/e5
python -m candgen.validate --dense-model models/e5
```

Абляция - те же команды с флагами, каждый запуск пишет свой отчёт:

```bash
python -m candgen.validate --no-dense
python -m candgen.validate --no-location
python -m candgen.validate --no-popularity
python -m candgen.validate --infm-in-query
python -m candgen.validate --max-queries 5000   # быстрый прогон на подвыборке
```

Тесты идут на синтетическом датасете той же схемы и не требуют настоящих данных:

```bash
pip install -r requirements-dev.txt
pytest
```

## Структура

```
candgen/
  data.py        загрузка, сборка train-запросов, разбиение по тексту, популярность
  text.py        токенизация, стемминг, символьные n-граммы
  bm25.py        BM25 на scipy.sparse
  dense.py       эмбеддинги e5
  indexes.py     всё, что считается по корпусу один раз (с кэшем)
  candidates.py  кандидаты из всех источников, их ранги и скоры
  features.py    признаки пар - одни для обучения, валидации и benchmark
  ranker.py      LightGBM LambdaRank
  pipeline.py    обучающие кадры и ранжирование по частям
  validate.py    оценка на hold-out
  submit.py      answer.csv
notebooks/01_eda.ipynb   разведка данных
tests/                   тесты и генератор синтетики
```

`answer.csv` в репозитории - ответ v3 (0.7429 на платформе). `python -m candgen.submit` его перезапишет.

## Что можно попробовать дальше

- 37% текстов benchmark-запросов встречаются в train. Объявления, которые выбирали по тому же тексту,
  можно добавить отдельным источником кандидатов.
- Дообучить e5 на парах из train (contrastive loss с негативами из BM25).
- Заменить стемминг на лемматизацию (pymorphy3) и сравнить на hold-out.
